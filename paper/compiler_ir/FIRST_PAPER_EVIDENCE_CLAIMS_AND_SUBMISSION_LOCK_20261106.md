## Research thesis and scoped claims

**C1, primary:** A bounded typed Model IR can tie independent operator-local architecture choices (`Phi`) to source-visible tensor-element contribution, commit, multi-reader consumption, last-use scratch release, actual emitted source identity, and issue order, and can reject selected invalid traces under explicit finite-model assumptions. **Not** arbitrary-graph formal soundness, RTL equivalence or cycle-accurate hardware semantics.

**C2, primary:** The same ordinary compiler exposes policy-independent complete-design transitions, a weight-private typed graph view, and three-valued (`CERTIFIED_E0 / REJECTED / UNKNOWN_E0`) source legality. Cached certified transitions may be selected without recompilation **after** a compiler-built candidate catalog. **Not** zero-cost masks, trained RL gains, increased exploration efficiency, or hardware QoR guarantees.

**Supporting evidence:** Actual full-network HLS source/CSim/CSynth and a later, separate same-schedule storage contrast show that architectural choices have nontrivial, often adverse resource–performance consequences. HLS cycles are not physical runtime; requested periods are not achieved periods. The R4 physical cohort is descriptive post-route mapping only; neither matched design is E4 timing+clean-DRC qualified. This hardware result must stay secondary to C1/C2.

## Performance and latency evidence contract

**Report all of:** (a) cycles to first complete result and any initiation interval, (b) source- and tool-attested HLS-estimated cycle and schedule/clock feasibility, (c) requested physical period and routed WNS/DRC, (d) timing-closed feasible period on a comparable implemented netlist when available, (e) compute latency only if compatible cycles and feasible period exist, (f) throughput, and (g) board end-to-end latency including DMA/DDR/buffering/CDC when measured.

Under a compatible qualified fixed-clock implementation, `compute_latency_ns = cycles_per_inference × feasible_period_ns`, with first-output latency and initiation interval not conflated; throughput may differ from inverse first-output latency. The original, strictly E3-qualified R4l HLS study reported **22,954 versus 22,602 worst cycles** and **9.857ns versus 9.500ns HLS-estimated clock periods**. Two transparent **derived E3-only runtime proxies** are (1) each arm's own HLS-estimated period: `22,954×9.857ns = 226.258µs` versus `22,602×9.500ns = 214.719µs`, an apparent 11.539µs reduction, and (2) a common 12ns requested period: `22,954×12ns = 275.448µs` versus `22,602×12ns = 271.224µs`, an apparent 4.224µs reduction. These proxies have different clock assumptions and neither is measured physical runtime. This is NOT a tool-measured physical or timing-closed latency, nor an achieved Fmax. For the R4 pair **there is no qualified feasible physical period**: both WNS values are negative, so **physical compute latency, achieved Fmax, real throughput and board latency are UNKNOWN**. In particular, multiplying source-attested E3 cycles by the **failed** 12ns requested clock does not produce an observed physical inference latency. An apparent BRAM reduction must be described alongside LUT/FF/timing costs, not as a Pareto-optimal or superior design.

## Benchmark non-superiority theorem under certified-only fixed-parent selection

In the newly implemented fair C2 direct/lazy/eager benchmark, for a fixed parent compiler state, a catalog of **8** actions and a query sequence with **D distinct requested actions**, the eager catalog necessarily invokes the compiler **8** times and a correct lazy on-demand cache invokes it **D ≤ 8** times (each actual source transition uses the same compiler). **Therefore eager precomputation cannot reduce total source compiler invocation count relative to lazy caching under this workload.** The only potentially favorable costs are API convenience, the ability to show the entire certified mask before choosing, or nontrivial source-status batch implementation optimizations (not currently measured). Wall-clock values are still empirical and influenced by cache and context; the benchmark is deliberately capable of confirming the eager strategy is **worse**. If this is the outcome, the C2 utility claim must be narrowed rather than inventing an efficiency gain.

**Consequence for publication:** Showing more accepted/invalid counts or rerunning masked self-consistency checks cannot establish C2 novelty. Either demonstrate a distinct capability (e.g., source-consistent policy-agnostic *typed* transition contracts plus independently validated UNKNOWN boundary behavior across held-out graphs/compilers), or present C2 as software infrastructure without pretending it is a separate algorithmic breakthrough. Strongest remaining independent science is source-to-generated-executable refinement plus a fair Allo capability comparison.
