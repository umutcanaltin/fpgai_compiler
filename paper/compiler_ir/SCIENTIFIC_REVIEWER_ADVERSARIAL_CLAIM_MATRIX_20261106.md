## 1. Actual scientific claim at issue

**C1 proposed narrow novelty:** a typed, finite compiler-source contract records (i) immutable source/functional identity, (ii) producer contribution and commit, (iii) multi-reader value readiness/last use, (iv) scratch address alias safety, and (v) explicit **operator-local Φ-dependent READ issue-order conformance**. It provides `safe`, `schedule-conformant`, `REJECTED`, `UNKNOWN` distinctions for admitted finite graphs. An emitted C++ runtime refinement must actually demonstrate these obligations on a held-out population before claiming implementation correspondence. This is **not** a formal proof for all graphs, a RAM-port cycle certificate, or the first verifier of accelerator schedules.

**C2 proposed narrow contribution:** a source-identity-pinned typed transition and tri-state policy-independent action interface that reuses actual compiler certificates. An eager catalog is not an algorithmic speedup over a lazy cache under the fixed-parent-eight-action source-call budget, and a self-evaluated action mask does not provide an independent oracle. Report this as engineering infrastructure unless genuine external capability and multi-state utility are independently established.

## 2. Falsifiable matched semantic counterexamples

Use one functional graph and identical initialized tensors/precision per pair; compare independent functional outputs, finite source trace, actual generated C++ witness, compiler contract and, where representable, independent external compiler output-equivalence. Predeclare a small admitted two-reader MatMul fanout, another fanout degree, and at least one graph outside the current admitted family (expected `UNSUPPORTED/UNKNOWN` unless the implementation genuinely supports it). No changed model weights or chosen tolerance after viewing results.

| Case | Functional output equality to canonical | Value/lifetime safety | Declared Φ issue-order conformance | Hypothesis/interpretation to test |
|---|---|---|---|---|
| A — canonical producer commit then readers in declared order | Yes | Yes | Yes | All functional and schedule judges should accept; actual generated C++ must reproduce typed events/access addresses |
| B — two independent reader executions swapped, without racing/reusing a live scratch value | **Yes is the intended control; verify independently**, not assume | Expected Yes | Expected No | If output-equivalent but schedule-nonconformant, demonstrates distinction between output **equivalence** and *a particular chosen temporal contract*. Rejection is not a functional bug. |
| C — reader consumes producer before COMMIT | Expected No / undefined read | Expected No | Depends on issue verifier | Both a data-lifetime validator and an external executable output checker should reject/differ when representable |
| D — overwrite a still-live producer scratch slot before its last reader | Expected No / corrupted for adversarial values | Expected No | Depends on issue verifier | Source address/ownership and actual C++ independent shadow witness should reject; this establishes a concrete data hazard, unlike B |
| E — source Φ owner/issue mapping deliberately altered while functional arithmetic remains unchanged | Output may remain equal | Can remain Yes | Expected No when against original declared Φ | Requires original requested mapping as part of what is being certified; do not mislabel a different valid schedule as unsafe |
| F — valid alternative Φ schedule **with a newly declared matching contract** | Expected Yes | Expected Yes | Expected Yes | Positive compositionality control: the compiler must not reject equivalent valid implementations merely because one canonical policy is preferred |
| G — unsupported operator/graph/precision or ambiguous concurrency | Unknown | UNKNOWN | UNKNOWN | Should fail closed/return unsupported and never be silently counted as REJECTED or accepted |

**Pass/fail** is NOT 'reject more'. A strong outcome is **correct three-way discrimination**: pass A/F, identify B/E as source-safe but nonconformant *to their original requested schedule*, catch the C/D hazards with independent execution witnesses, and refuse unsupported G. If an external compiler can represent and verify an analogous temporal contract, **acknowledge equivalence/overlap**. If G is unsupported internally, do not select only representable positive cases.

**Existing empirical distinctions:** R3j's original 24-profile/216-trace predicate recombination is an internal logical conjunction, not a separately compiled A/B comparator; R3e/R3g add finite independent oracle controls; newer 54-profile/486-trace original C1 source event checks had zero observed oracle disagreement, still **same topology**; earlier separately pinned six-graph R2r source C++ mutation runs rejected 216/216 selected corruptions. A new 54-profile bridge proposes **108 actual GCC source executions** but remains **unexecuted**; it should test A-like canonical behavior and will not itself establish all B–G experimental claims.

## 3. External baseline design — mandatory, not token citation

**Allo official 2024 paper and tutorial:** https://doi.org/10.1145/3656401 and https://cornell-zhang.github.io/allo/gallery/dive_05_verifier.html. The official tutorial explicitly verifies functionally equivalent but structurally different GEMM schedules using `allo.verify` and rejects a changed reduction that overwrites accumulation. It is evidence that schedule transformations and output equivalence **already have a verifier**. The existing exact-source-pinned isolated [R3i Allo runbook](R3I_ISOLATED_ALLO_CAPABILITY_RUNBOOK_20261104.md) is NOT EXECUTED and focuses on output equivalence, not an identical Φ typed-event object.

An executed fair baseline requires, for every case A–G: exact Allo revision, official supported API/version, source/IR, independently confirmed output behavior, emitted source schedule (if available), result status, stdout/stderr, and reason for nonrepresentability. The classifications are **`REPRESENTABLE_AND_VERIFIED`, `REPRESENTABLE_BUT_REJECTED`, `UNSUPPORTED_REPRESENTATION`, `ENVIRONMENT_FAILURE`, `UNKNOWN`**. A failed import, missing MLIR/PAST, unsupported construct, timeout or absent API claim is NOT a negative correctness result. Do not infer novelty from different language syntax or by comparing one system's Φ trace check with the other's whole-output-only verifier.

**CODO (ISCA 2026):** https://arxiv.org/abs/2604.12618 and https://github.com/sjtu-zhao-lab/codo-artifact. CODO already detects coarse/fine dataflow violations and optimizes communication/scheduling. It is a serious adversarial comparator for a claimed producer/consumer/communication timing contract. Compare at a supported executable kernel/IR level; cite CODO's declared scope and report whether a concrete identical hazard is expressible. A hardware QoR baseline is only fair when normalized to equal functionality, precision, device, clock constraint, source data width, memory/IO assumptions and placement run conditions.

**Allo/CODO capability is not logically subsumed or refuted by our finite selected mutations.** The novel remainder, if there is one, must be stated at the level of a checkable independent operator-local Φ-parameterized source-event contract + actual emitted-address/read witnesses + source-hash-safe interface; peer reviewers must independently agree that this differs from existing methods substantively. If not, narrow to a reproducible engineering case study rather than a priority claim.

## 4. End-to-end E0/E1/E2/E3/E4 evidence boundaries

| Stage | Minimum accepted evidence | What NOT to infer |
|---|---|---|
| E0 source semantics | Complete finite trace/certificate and independent oracle, explicitly selected negative/positive controls, original trace SHA | All-input formal proof or downstream generated-code equivalence |
| E1 executed emitted source | Same original graph/source identity, real generated GCC compilation and execution, actual address-adjacent events, intermediate/final independent numerical reference, source SHA, both layouts | Native Vitis fixed-point/RTL correctness or FPGA cycle/BRAM timing |
| E2 C simulation | Actual Vitis HLS CSIM with original numeric constraints and source/ROM hash receipts; report tolerance and max error | Synthesis physical feasibility |
| E3 HLS estimates | Estimated cycles, target and estimated clock, resource vector, strict timing qualification, numeric E2 ancestry | Hardware realized latency or Fmax; cycles alone not latency |
| E4 routed implementation | Real routed timing **met**, explicitly classified clean DRC, exact board/part and constraints, complete unchanged mapped source + link to cycle/latency semantics | Board DMA throughput without real measured end-to-end inference |

The **original** same-schedule storage contrast demonstrates **routed BRAM 7→4, DSP 24→21, LUT 1282→1710, FF 883→1022 and WNS −2.170→−3.718ns** at requested 12ns, with both arms **TIMING FAILED and DRC NONCLEAN**. This is *descriptive Pareto tension*, not an E4 win, achieved Fmax or compute latency. The original R4l HLS estimates **22,954→22,602 worst cycles**, HLS periods **9.857→9.500ns**, derived HLS-only approximate runtime proxies **226.258→214.719µs** or **275.448→271.224µs** under common 12ns target. Neither proxy is feasible physical board latency.

**Only if hardware performance is part of the primary novelty claim**, preregister a **new** feasible-clock/clock-constraint sweep with exact fixed source scheduling, both layouts, independently attested post-route WNS, full LUT/FF/DSP/BRAM/URAM, DRC and truthful per-inference latency/II measured on matched input/burst data. Predefine a clock set and ≥3 independent implementation seeds, complete all cases including timing failures, power and interface assumptions, and board-on-target DMA timing if claiming real inference. Original R4p and R4u permanently locked; never clear locks, rerun or overwrite. New tool runs require deliberate workstation approval. OOC timing is not board throughput.

## 5. C2 useful effect versus a lazy baseline: explicit rejection criterion

Original pinned 324-row source-cost dataset uses six R3f fixed parents, three seeds, 1/8/32 queries, certified-only request streams, and **48 excluded preflight compiler calls**; source outputs match. This is valid for descriptive measurements; an eight-action eager catalog uses exactly eight compiler transitions and lazy caching uses only **D ≤ 8**, the distinct requested actions. Therefore **eager cannot be a source-call-count improvement over lazy for this workload**. The newly written read-only SHA-pinned C2 report analyzer is pending author test/run; publish all median/pair CPU results including losses.

A scientifically stronger utility test needs *blind unfiltered* multi-state action requests, including rejected and unknown, with the same total CPU-source-compiler budget and same proposer. Compare raw direct transitions, lazy certified action memoization, eager full-source mask and a genuinely independent graph/action validity oracle. Charge **all** preflight, validity mask, source translation, certificate, cache and selection time; report time to first E0-certified state, number of attempted actions, rejected/unknown fraction, source compile calls, wall CPU time, source-memory/IR metric (not hardware throughput), and honestly what cannot be measured without E3/E4. Use new source SHA and new create-only original results, never reinterpret the fixed original certified-only sample as this more difficult test.

**Decision on manuscript framing:** If C1 true value is source conformance with executable witness and C2 never outperforms lazy caching, paper should be **one central C1 contribution** with C2 described as a enabling policy-independent interface. A two-equal-contribution framing requires distinct independently validated C2 novelty/utility. Claims must be downgraded if Allo/CODO already provide the purported feature or if the executable source bridge fails.
